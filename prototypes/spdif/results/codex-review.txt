## Findings

- **Medium — CD channel status sets the L bit to the wrong meaning.** [iec60958.ml:54]( /home/matthias/prog/janestreet/emulator-wt-spdif/prototypes/spdif/iec60958.ml:54) sets `l_bit = 1`, and [iec60958.ml:26–29]( /home/matthias/prog/janestreet/emulator-wt-spdif/prototypes/spdif/iec60958.ml:26) says that means “original / commercially released.” IEC 60958-3:2006 says that for laser-optical products, L=0 means commercially released prerecorded software and L=1 means “no indication.” The standard also identifies the IEC 60908-compatible CD category separately. So the transmit tests consistently validate the encoder’s chosen bit, but do not establish that this CD metadata is correct. [IEC 60958-3:2006](https://www.standards.iteh.ai/catalog/standards/iec/1a9bb047-5b10-453b-be18-e1d3dee6634b/iec-60958-3-2006) [IEC 60958-3:2021, copyright and category fields](https://standards.iteh.ai/catalog/standards/iec/e027efe2-dc8c-40ba-a1f8-004f2925c196/iec-60958-3-2021)

- **Medium — the reported TX jitter is not measured at the specified edge set.** [main.ml:281–285]( /home/matthias/prog/janestreet/emulator-wt-spdif/prototypes/spdif/main.ml:281) measures ideal placement at *every UI boundary*. The line only transitions at boundaries whose transition bit is 1; the actual transition flag is present in `r.bounds` but the jitter calculation does not use it ([tx_fw.ml:47–50]( /home/matthias/prog/janestreet/emulator-wt-spdif/prototypes/spdif/tx_fw.ml:47)). AES3/IEC intrinsic jitter is measured at data-transition zero crossings. Thus 0.0117 UI is a useful model statistic, but it does not by itself prove compliance at the transmitted edges. Recompute TIE and the filtered peak using only actual transition edges before claiming the 0.025 UI limit is met. The one-pole high-pass approximation and least-squares trend removal look reasonable; the sample points are the problem. [IEC 60958-1 jitter requirement](https://www.standards.iteh.ai/catalog/standards/iec/a48e35a8-f500-4bcd-a3b5-cf8869dd7b9a/iec-60958-1-2008)

- **Medium — “clean” permits record loss and ignores trailing error count.** [main.ml:82–92]( /home/matthias/prog/janestreet/emulator-wt-spdif/prototypes/spdif/main.ml:82) omits both `startup_errors` and `trailing_errors` from `rx_err`, while `clean` accepts any comparison count at or above its `expect`. Random and control cases use 836 against 840 sent subframes; the tolerance criterion uses 430 against 440. A run can therefore pass with several missing records, and can pass with multiple errors classified as trailing. The README discloses startup/trailing exclusions, but the pass result does not bound those counts tightly enough to support “clean.” The resynchronising compare does count mismatches, so a corruption that it compares will fail; it does not make the missing-record allowance fail.

- **Low — oracle independence is algorithmic, not independent of the protocol interpretation.** `oracle.ml` classifies edge intervals rather than decoding the encoder’s byte stream, so it is a meaningfully different implementation. But its preamble intervals and slot order are explicitly the same assumptions as the encoder’s: compare [oracle.ml:6–10]( /home/matthias/prog/janestreet/emulator-wt-spdif/prototypes/spdif/oracle.ml:6) with [iec60958.ml:8–14]( /home/matthias/prog/janestreet/emulator-wt-spdif/prototypes/spdif/iec60958.ml:8), and its audio reconstruction at [oracle.ml:95–97]( /home/matthias/prog/janestreet/emulator-wt-spdif/prototypes/spdif/oracle.ml:95). That shared interpretation is expected, but an error in those assumptions could make encoder/oracle agreement misleading. The sigrok comparison is useful independent evidence for preambles and decoded fields, though the README says it does not check parity. So “UI for UI equal” is not wholly vacuous, but the oracle is not an independent standards adjudicator.
