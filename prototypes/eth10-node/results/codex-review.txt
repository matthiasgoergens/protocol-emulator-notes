## Concrete problems

1. **The receive tolerance tests can pass without demonstrating tolerance.** In [rx_tests.ml](/home/matthias/prog/janestreet/emulator-wt-proto-eth10/prototypes/eth10-node/rx_tests.ml:290), the clock-offset sweep only fails the test when `p <= 10000.0` and fewer than all frames are recovered. In the jitter sweep at lines 299–307, the test fails only if there are false accepts; it never requires any frames to be recovered. The preamble-loss check at lines 318–319 similarly checks recovery only for preambles of at least 10 bits. A receiver that accepts no jittered frames, or none with short preambles, can therefore pass those parts.

2. **The clause 14 checker does not enforce its stated NLP timing on the initial idle interval.** In [clause14.ml](/home/matthias/prog/janestreet/emulator-wt-proto-eth10/prototypes/eth10-node/clause14.ml:133), pulse spacing is checked only after `have_prev` becomes true. The first pulse is not checked against the start of observed idle, so a waveform with an arbitrarily late first link pulse can pass if its ending tail is short enough. The checker also does not require any NLP at all: the tail check only rejects silence *longer* than the maximum interval (lines 162–163). This leaves the start-of-idle timing unverified.

3. **The host oracle can miss incorrect IP header fields in echo replies.** In [host_stack.py](/home/matthias/prog/janestreet/emulator-wt-proto-eth10/prototypes/eth10-node/host_stack.py:117), it checks IP source and destination, then checksum validity, but does not compare the reply’s other IP header fields with the request. A reply that changes TTL, identification, TOS, or flags while recomputing a valid IP checksum can pass. The comment at [engine.ml](/home/matthias/prog/janestreet/emulator-wt-proto-eth10/prototypes/eth10-node/engine.ml:20) says TTL and identification are kept, but the host check does not verify that claim.

4. **The RX “never accepts a frame with wrong bytes” claim is stronger than the CRC test establishes.** [rx_path.ml](/home/matthias/prog/janestreet/emulator-wt-proto-eth10/prototypes/eth10-node/rx_path.ml:73) uses the CRC residue as the frame acceptance check. That detects the tested corruptions, but CRC-32 is not a guarantee that every altered byte sequence is rejected: different data can have the same residue, and an altered frame with a correspondingly valid FCS passes. The tests in [rx_tests.ml](/home/matthias/prog/janestreet/emulator-wt-proto-eth10/prototypes/eth10-node/rx_tests.ml:343) exercise 200 generated corruptions, not all possible wrong-byte frames.

The recorded results in `results/*.txt` show those tested cases passing, but they do not close these coverage gaps.
