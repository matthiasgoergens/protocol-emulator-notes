    39	## 1. Capacity: what fits on one sequencer
    40	
    41	A thread owns exactly a quarter of the slots whether it uses them or not. At 60 MHz that is 15
    42	million slots a second per thread. So the budget is **threads (4) and pins**, not a fraction of
    43	slots. A protocol either fits in a thread at its rate or it does not. Then the question is
    44	whether the thread keeps its deadlines, which the budget analysis in §4 checks to the slot.
    45	
    46	Merging several slow protocols into one thread would make fractions matter. The compiler could do
    47	that by interleaving their schedules (PLAN.md, "thread interleaving as disjunctions"), but it is
    48	not done here.
    49

    51	against an independent model; "branch" means another agent's branch that is not on master yet;
    52	"estimate" means an instruction count by hand.

   102	On this evidence the few units that buy the most concurrency are:
   103	
   104	1. **The mailbox.** Every bridge and analyser needs it, and it is the only one that changes the
   105	   ISA.
   106	2. **The streamer/sampler.** It turns the one protocol that takes all four threads into one that
   107	   takes none.
   108	3. **Stuffing and CRC.** Without them a CAN or USB node needs the host or an extra thread.
   109	
   110	The oversampling front end matters for rates above about 1.5 Mbit/s per thread.
   111	
   112	## 2. How threads talk: three options
   113	
   114	**(a) Through the host.** Every byte costs an OUT on one thread, a host read, a host write and
   115	an IN on the other. Latency is the host's round trip: microseconds over SPI or USB from the
   116	RP2040, and not deterministic. The host link's bandwidth is shared by every bridge. The chip also
   117	stops being standalone, which rules out the CAN analyser. Not built: it is the status quo.
   118	
   119	**(b) Spare pins looped back, with no ISA change** (`loopback.exe`, base ISA and RTL unmodified).
   120	Three pins: *valid*, *ready* and *data*. Because the barrel fixes the phase between two threads,
   121	one rendezvous suffices. The sender's SHO in slot k is seen by the receiver's SHI in slot k,
   122	eight bits in a row.
   123	
   124	- **Measured:** 256 random bytes in order. **56 cycles per byte** (1.07 MB/s at 60 MHz), 15 + 13
   125	  words. The RTL matches the interpreter on every cycle.
   126	- **Costs:** both threads are fully occupied for the whole transfer, nothing is buffered, and the
   127	  sender waits until the receiver is at its poll.
   128	- **Control:** with the sender one slot early, 0 of 256 bytes arrive correctly. The link exists
   129	  only because the timing is exact. That is a fun property, but the link costs three pins and two
   130	  threads' attention.
   131	
   132	**(c) A mailbox, the choice made here** (`isa_mb.ml`, `sequencer_mb.ml`). Measured on the same
   133	test: **12 cycles per byte** (5 MB/s), 3 + 3 words, no pins. Each side spends 2 of every 3 of its
   134	slots, and the inbox buffers.
   135	
   136	### The ISA proposal
   137	
   138	It is a strict extension of the base ISA. Opcodes 0xE and 0xF were NOP; SHO bits 6..3 were
   139	unused.
   140	
   141	- **Parameters.**
   142	  - `pc_bits`: 6 is the base; 7 gives 128 words per thread.
   143	  - `depth`: 1, 2 or 4 bytes per inbox.
   144	  - Every address field is the low `pc_bits` of the word.
   145	- **State.** One inbox per thread, a FIFO of `depth` bytes. At most one instruction executes per
   146	  cycle, so there is at most one inbox operation per cycle in the whole core. The barrel schedule
   147	  is the arbiter, and no second port is needed.
   148	
   149	```
   150	E  MBX    dir[11] ch[10:8] 0[7] fail[pc_bits-1:0]
   151	          ch 0..3: inbox ch;  ch 4..7: generic port ch-4 (outside the core)
   152	          SEND (dir 0): target can accept -> push acc, proceed; else dl = 0 -> jump fail; else stay
   153	          RECV (dir 1): source has a byte -> acc <- pop, proceed; else dl = 0 -> jump fail; else stay
   154	F  WAITC  val[11] cond[10:7] fail[pc_bits-1:0]
   155	          cond 0..7: acc bit; 8..11: inbox cond-8 full; 12..15: flag input cond-12
   156	          condition = val -> proceed; else dl = 0 -> jump fail; else stay
   157	7  SHO    pin[11:9] msb[8] od[7] cap[6] cpin[5:3]   (capture option, for full duplex)
   158	          with cap set, pin cpin is sampled in the same slot and enters the vacated bit
   159	```
   160	
   161	**Semantics that keep timing exact.**
   162	
   163	- A blocked SEND, RECV or WAITC stays in its own slot exactly as WAITP does. The round-robin never
   164	  changes, so a full or empty mailbox cannot move another thread's edges.
   165	- Every wait is bounded by the thread's own deadline and then jumps to `fail`. An unbounded wait
   166	  has to be written explicitly as `fail` = its own address. The bridges use that only where
   167	  waiting for ever is the right behaviour: an idle thread waiting for work.
   168	- Deadlock between threads is therefore a property of the programme, visible in its text, never of
   169	  the schedule. With `dl = 0`, `WAITC` on an acc bit is a conditional branch in one slot. This was
   170	  the missing piece for parsing bytes: the base ISA could only branch on pins, the counter and
   171	  deadlines.
   172	- Ports make generic blocks first-class: the Ethernet receiver, memory write ports, the video pin
   173	  stage and the CAN frame interface. In-port handshakes match IN and out-port handshakes match
   174	  OUT.
   175	
   176	**Verification of the variant** (`results/lockstep.txt`):
   177	
   178	- **Lockstep of the RTL against the interpreter:** 300 random programmes × 2,000 cycles for each
   179	  of four configurations, 0 mismatching cycles. Half the programmes are mailbox-heavy. Coverage
   180	  per configuration: 1,286–1,987 inbox pushes, 980–1,257 pops, 138,555–375,689 cycles with a
   181	  full inbox, and 1,997–3,062 port transfers in each direction.
   182	- **Strict extension:** with `pc_bits = 6`, the variant's RTL matches the base interpreter on
   183	  programmes without the new fields. 0 mismatches.
   184	- **Planted bug:** an inbox that never reports full is caught in 14 of 50 programmes (22,534
   185	  cycles). Only programmes that fill an inbox can show it.
   186	
   187	**Area** (Yosys 0.62, sg13g2 typical, flattened, instruction memory external; the base
   188	re-synthesised with the same Yosys):
   189	
   190	| configuration | µm² | flops | vs base |
   191	|---|---|---|---|
   192	| base sequencer | 17,263 | 179 | – |
   193	| mailbox, depth 1, 64 words | 22,568 | 227 | +31 % |
   194	| mailbox, depth 2, 64 words | 26,362 | 267 | +53 % |
   195	| mailbox, depth 4, 64 words | 32,058 | 339 | +86 % |
   196	| mailbox, depth 2, 128 words | 26,996 | 271 | +56 % |
   197	
   198	The inboxes are cheap in logic and dear in flops at 49 µm² each. Depth 2 is 64 data flops, 12
   199	pointer flops and 12 port-register flops, and the rest is the port and condition multiplexers.
   200	Two cheaper stores are worth measuring:
   201	
   202	- **latches:** about 31 µm² a bit, per the PLAN's latch table;
   203	- **a shared pool:** one small FIFO or latch array addressed by inbox. That is enough because
   204	  only one operation happens per cycle.
   205	
   206	The demos show depth 1 is enough when there is flow control: the UART ↔ I2C backpressure run
   207	passes at depth 1. Depth 4 was needed only where a thread holds three bytes while waiting for a
   208	CAN frame's status.

   210	## 3. The demonstrations
   211	
   212	### Ethernet to TV (`ethtv.ml`, `video.ml`, `video_fw.ml`; the flagship)
   213	
   214	Raw 10BASE-T frames (EtherType 0x88B5), each carrying one source scanline, are received while
   215	NTSC colour video is generated by chasing the beam. Both run from one 60.852 MHz clock (17 × fsc),
   216	concurrently.
   217	
   218	**Capacity split:**
   219	
   220	- **Receive:** the 10BASE-T receiver RTL, then a header matcher (broadcast, 0x88B5), then two
   221	  in-ports.
   222	- **T0 (parser):** takes the line number, writes 32 pixel bytes into a line buffer of four
   223	  gain-cell rows, drains the padding, and commits the row only if the CRC was good. It uses 21
   224	  words and about 25 % of its slots during a frame.
   225	- **T1 (video timing):** sync and blanking by SETP on four luma pins, and burst and playback by
   226	  commands to the pin stage, every edge on an exact slot. 84 words. Every line is 967 slots, which
   227	  is 3,868 clocks, 227.5 subcarrier cycles plus 1/17.
   228	- **The stage, all generic:**
   229	  - the NCO's two chroma pins: pin A is high 9 phases of 17 and pin B 8, so their sum is flat;
   230	    the mean phase is the hue and the phase difference the saturation;
   231	  - a memory streamer (64 pixels × 48 clocks);
   232	  - a 16-entry lookup table, chosen by the host from a prediction of what a TV decodes.
   233	- **T2, T3:** an SPI master and a UART transmitter, unrelated to the video, to show isolation.
   234	
   235	**Why one scanline per frame means line doubling:** a minimum Ethernet frame with preamble and
   236	gap takes 67.2 µs, longer than an NTSC line (63.6 µs). One frame per line cannot keep up. Each
   237	source line is shown on two TV lines, 120 source lines per field.
   238	
   239	**The line buffer's lifetime contract.** A row is written when its frame arrives and read on two
   240	TV lines. The first read writes each byte back, which is how gain cells are refreshed: a read
   241	followed by a write. The longest write-to-read interval measured is **102.9 µs**, under the
   242	120 µs of thin-oxide rows at tt/27 °C. Three runs show the contract matters:
   243	
   244	- **Thin-oxide rows at 85 °C (8 µs):** every read violates it. The cells' one-sided decay turns
   245	  the picture black: 172 of 1,920 blocks correct.
   246	- **No refresh on the first read:** the second reads reach 166.5 µs, with 3,578 violations and
   247	  1,088 of 1,920 blocks correct.
   248	- **A reordered pair of frames** (line 91 arrives before line 90): line 91 lives 264 µs. That
   249	  breaks thin-oxide rows (source line 91 decays, 1,904 of 1,920 correct) and is fine in
   250	  thick-oxide rows (≥ 3 ms: 1,920 of 1,920). Reordering by one frame costs one frame time of
   251	  lifetime. The row type should be chosen by the reorder window, not only by the line time.
   252	
   253	**Results** (the unmodified `../composite-video/tv.py` finds syncs, locks to each line's burst and
   254	decodes the field; the judge samples each 8-pixel block's centre):
   255	
   256	- **Main run:** RTL and interpreter agree on every one of 1,015,416 cycles, and the software TV
   257	  decodes **1,920 of 1,920 blocks** to the colour that was sent. The corrupted frame and the
   258	  filtered frame (wrong EtherType) come out as black lines, as they must.
   259	- **Line periods:** all 258 are exactly 3,868 clocks. The control with one extra slot in the
   260	  active line decodes fine, because a TV tolerates it, but its periods read 3,872. The timing
   261	  contract is checked on the waveform, not only on the picture.
   262	- **Isolation:**
   263	  - the composite is identical cycle for cycle with the neighbours, without them, and under 4
   264	    pairs of random neighbour programmes;
   265	  - the neighbours' pins are identical with and without Ethernet and video.
   266	- **Picture:** `out/ethtv_main.png`.
   267	
   268	**A bug in the shared receiver, found here.** `../ethernet-10base-t/eth_rx.ml` does not clear its
   269	byte shift register at frame start. On back-to-back frames the previous frame's last bits plus
   270	the new preamble matched 0xD5 one bit early. Frame 113 (after 112, gap ≥ 9.6 µs) was read with
   271	its header shifted by a bit (0x55 as 0xAA) and dropped. This happened deterministically, with 0
   272	to 3 ns of jitter. Clearing the register fixes it. The fix is in a local copy,
   273	`eth_rx_fixed.ml`, which the demo uses; `rx_shared` in `results/ethtv.txt` reproduces the bug.
   274	The shared file is left for its owner (the proto-eth10 branch).

   276	### CAN bus to TV: a standalone analyser (`cantv.ml`, `can_standin.ml`)
   277	
   278	- **Header:** flashes red for 30 fields after an error frame.
   279	- **Waveform:** the last 64 bus bits scrolling, as three two-level traces (bus, node A's TXD,
   280	  node B's TXD). Stuff bits are yellow; the bit where a node lost arbitration is red on its trace.
   281	- **ID table:** eight rows. Each shows the last identifier seen in its slot (ID10..ID8), with its
   282	  control bits, and an activity bar. The bars are eight saturating counters: +32 per frame, −4 per
   283	  field.
   284	
   285	![analyser](out/cantv_noerr.png)
   286	
   287	**Threads:**
   288	
   289	- **T0:** writes each bit's code into a ring row. 3 words, 2 instructions per bit.
   290	- **T2:** renders frame events. It uses a branch tree on the ID and keeps two bytes in its own
   291	  inbox while it branches, so the mailbox doubles as scratch memory. 74 words.
   292	- **T1:** the video-timing thread, identical to Ethernet to TV.
   293	- **T3:** the slot for the CAN RX thread. Here it runs an unrelated UART, and a stand-in supplies
   294	  the events.
   295	
   296	**Stage:** memory rows plus a per-line descriptor list (row, palette bank, bar), which is a
   297	display list as DMA engines have.
   298	
   299	**Results:** 79 transmissions, 12 of them arbitration contests, one error frame.
   300	
   301	- **Stage against the reference analyser:** the stage's output matches an independent reference
   302	  analyser, which sees only the event history, on **15,360 of 15,360 pixels**. The counters and
   303	  the flash state are also equal.
   304	- **Through the software TV:** it decodes **15,360 of 15,360 pixels** to the expected palette
   305	  colour, both with the error frame and without it (then no flash).
   306	- **RTL against the interpreter:** 0 mismatches.
   307	- **Isolation:** holds.
   308	- **Lifetime:** display rows are re-read once per field, so the longest interval is **15.95 ms**.
   309	  That fits thick-oxide rows at tt (12–20 ms) only at the upper end, and fails at the worst case
   310	  (≥ 3 ms). A standalone display needs a refresh sweep at least twice per field, or SRAM. This
   311	  is a real cost the Ethernet buffer does not have.

   313	### UART ↔ I2C, UART ↔ SPI (`bridges.ml`, `bridge_lib.ml`)
   314	
   315	**Bridge A (UART ↔ I2C)** is four threads:
   316	
   317	- **T0, UART receive:** raises RTS when the I2C thread's inbox is full.
   318	- **T1, I2C master:** runs a byte code (START, STOP, WRITE b, READ, ACK, NACK) and honours clock
   319	  stretching on every SCL rise, bounded by its deadline. 99 words.
   320	- **T2, UART transmit.**
   321	- **T3:** an unrelated SPI master.
   322	
   323	**Bridge B (UART ↔ SPI):** a full-duplex SPI master built on SHO with capture, with an I2C master
   324	as T3.
   325	
   326	**The other side of each bridge:**
   327	
   328	- **Host:** a UART model that honours CTS, with random gaps and a baud error.
   329	- **Devices:** a bit-level I2C slave with random clock stretching (up to 1,500 cycles) and
   330	  a bit-level SPI memory.
   331	- **Expected results:** transaction-level reference models, written separately.
   332	
   333	**Results** (`results/bridges.txt`):
   334	
   335	- **Main runs**, RTL in lockstep: 71/71 and 56/56 answers exact. The device registers and the
   336	  decoded I2C bus bytes are exact too.
   337	- **Constrained random:** 24 of 24 runs pass (12 seeds × 2 bridges). Traffic mixes register
   338	  writes and reads, 10 % to an absent device, host gaps of 0–2 bits, baud errors of −1.6 % to
   339	  +1.6 %, and slave stretching of 0–900 cycles.
   340	- **Backpressure** (no host gaps, the slave stretching up to 1,500 cycles): passes at inbox depth
   341	  1, 2 and 4. RTS is high for 47,081, 22,261 and 9,137 cycles, and the host waits on CTS for
   342	  45,005, 20,649 and 8,729 cycles.
   343	
   344	**Controls, each of which must fail:**
   345	
   346	- **A dropped push:** fails on both bridges.
   347	- **Newest-first pop:** fails on A. On B it is **vacuous**, because B's inbox never holds two
   348	  bytes. This is recorded, not hidden: an ordering fault needs occupancy ≥ 2 to show.
   349	- **Two pushes swapped, swept over positions 20–69:** 82 of 82 swaps of different bytes caught.
   350	  The 18 swaps of equal bytes are invisible to any checker.
   351	- **A host ignoring CTS against the slow slave:** 21 overflows reported on the host channel, and
   352	  the answers go wrong.
   353	- **The receiver over budget:** see §4.
   354	
   355	**A deadlock the controls found.** In the first version, a byte that arrived while RTS was high
   356	(the path that keeps listening when stopped) returned to idle with RTS still high. A host that
   357	honours CTS then waited for ever: the over-budget run hung for 6 million cycles with RTS high.
   358	The fix lowers RTS on the normal path whenever there is room.
   359	
   360	### I2C ↔ CAN (`can_bridge.ml`): a CAN node fronting an I2C sensor
   361	
   362	- **T0, translator:** buffers each request's three data bytes in its own inbox until the frame's
   363	  status arrives, because a CAN node may act only after the end of frame. Frames with an error
   364	  are dropped before anything reaches the I2C bus.
   365	- **T1:** the unchanged I2C master.
   366	- **T2, assembler:** returns response frames.
   367	
   368	**Results:**
   369	
   370	- **Six seeds pass:** 25–28 responses each. The responses, I2C bus bytes and device registers
   371	  equal the reference, with the RTL in lockstep.
   372	- **Corrupted requests** (1 in 10) never reach the bus.
   373	- **Isolation:** holds.
   374	- **Mailbox faults:** a dropped push and a swapped pair are both caught.

   376	## 4. Budgets are exact: the receive-slack edge
   377	
   378	The UART receiver samples the stop bit at slot 9.5 B, measured from the poll that saw the start
   379	bit. It must be polling again by slot 10 B, because the next start bit can arrive then. The
   380	static count of instructions on that path gives the slack:
   381	
   382	- B/2 − 5 on bridge A (with the RTS check);
   383	- B/2 − 3 on bridge B.
   384	
   385	Adding NOPs to the path at exact baud with back-to-back bytes (`results/bridges.txt`):
   386	
   387	| bridge | extra slots | slack | result |
   388	|---|---|---|---|
   389	| A | +3 | 0 | 97/97 |
   390	| A | +4 | −1 | fails, 59 framing errors reported |
   391	| B | +5 | 0 | 67/67 |
   392	| B | +6 | −1 | fails, 50 framing errors reported |
   393	
   394	The prediction holds to the slot. At exact baud the next edge keeps its phase against the

   398	## 5. Isolation: the proof
   399	
   400	A thread's next state depends only on its own registers, its instruction, the pins it reads, and

   402	names no shared channel has the same pin trace whatever its neighbours do. Each demo checks this
   403	directly:

   407	  neighbour's pins and own inbox, including branches, waits and mailbox traffic);
   408	- the neighbour's pins are identical with the protocol idle and under different traffic.

   418	## 6. The CAN bridges when proto-ps2-can lands: plan and interfaces
   419	
   420	**The clash.** That branch's ISA variant (`isa_v.ml`) also takes the two free opcodes:
   421	
   422	- **E = JC:** jump if a condition holds (acc bit, CRC = 0, stuff, byte boundary, last bit).
   423	- **F = CFG:** CRC and stuffing configuration, and `cnt <- acc`.
   424	- **SHO bits 6..5:** feed the CRC and stuffing trackers, where this variant puts the capture
   425	  option.
   426	- **The programme counter:** 8 bits.
   427	
   428	The two variants cannot both be merged as they are. A unification that keeps both sets of
   429	programmes expressible:
   430	
   431	- **One conditional instruction** with this variant's wait semantics (dl = 0 is JC's jump).
   432	  - **Conditions:** JC's (acc bits, crc0, stuff, byte, last1) plus "own inbox non-empty",
   433	    "target inbox full" and two flags.
   434	  - **Encoding:** four bits of condition plus a polarity bit leaves 7 address bits, so the pc is
   435	    7 bits or the polarity goes.
   436	- **MBX takes the opcode that HALT frees**, since HALT ≡ `JMP self`. The assembler keeps HALT as
   437	  a pseudo-op. Old binaries with 0xD000 need recompiling, which the protocol compiler does
   438	  anyway.
   439	- **SHO:** capture moves to a fixed partner pin (`cpin = pin xor 1`) in one bit, next to crc and
   440	  stf.
   441	- **`cnt <- acc` (CFG 3)** is wanted here too. It would have removed the branch tree on DLC and
   442	  the fixed three-byte request format.
   443	
   444	**Interfaces for the bridges:**
   445	
   446	- **CAN RX thread → mailbox:** its tagged OUTs become SENDs to an inbox. The tag needs either a
   447	  channel per tag class or tag bits in the message. The minimal version is two channels: bit
   448	  events for an analyser, and frame events.
   449	- **Data packing:** after the three header chunks, data bytes should be byte-aligned. The branch
   450	  currently packs "7 bits followed by 8-bit chunks", which a bridge thread could only realign with
   451	  shifts. `can_bridge.ml` uses the aligned form: `0xA1 c1 c2 c3 d0 .. 0xA2 status`.
   452	- **CAN TX thread ← mailbox:** it takes `c1 c2 c3 d0 ..` and stuffs and adds the CRC on chip,
   453	  with the branch's trackers. Today it takes a stream the host has already stuffed.
   454	- **Thread budget for I2C ↔ CAN:** CAN RX, CAN TX, bridge and I2C master make four threads, which
   455	  fits only if the translator and the assembler become one thread. They already run strictly one
   456	  after the other: the translator waits for the assembler's done token.
   457	- **The analyser:** the CAN RX thread's raw bit and stuff reports feed the bit renderer, and its
   458	  SOF, header and END reports the frame renderer. Exactly the stand-in's events.

## Real problems

- **The strict extension claim fails at `pc_bits = 7`.** The base ISA uses only the low six address bits for `JMP`, `JNZ` and `WAITP` ([base `isa.ml`](/home/matthias/prog/janestreet/emulator-wt-multi-proto/prototypes/deadline-sequencer/isa.ml:17), [lines 25–26]). The variant uses the low `pc_bits` bits for those instructions ([`isa_mb.ml`](/home/matthias/prog/janestreet/emulator-wt-multi-proto/prototypes/multi-proto/isa_mb.ml:10), [line 131]; [`sequencer_mb.ml`](/home/matthias/prog/janestreet/emulator-wt-multi-proto/prototypes/multi-proto/sequencer_mb.ml:45)). Thus a legacy-format control word with bit 6 set in its otherwise-unused address field branches to a different address under the 7-bit variant. The lockstep extension check uses **only** `pc_bits = 6` ([`lockstep.ml`](/home/matthias/prog/janestreet/emulator-wt-multi-proto/prototypes/multi-proto/lockstep.ml:58)), so it does not test this case.

- **Pin-trace independence needs a pin-ownership condition.** A thread that names no shared inbox or port can still write a pin another thread writes. The interpreter stores pin outputs as shared state ([`isa_mb.ml`](/home/matthias/prog/janestreet/emulator-wt-multi-proto/prototypes/multi-proto/isa_mb.ml:90)); `SETP` and `SHO` update it ([lines 145–147, 153–160]). So its global pin trace can depend on a neighbour even when it names no mailbox or port. The README’s isolation claim is supported only for demos whose neighbour programmes are confined to their own pins ([`README.md`](/home/matthias/prog/janestreet/emulator-wt-multi-proto/prototypes/multi-proto/README.md:398), [lines 405–408)).

## Edge-case comparison

Static inspection found no definite interpreter/RTL mismatch in the requested SEND/RECV/WAITC/SHO cases:

- At depth 1, full detection is `count == depth` in the RTL ([`sequencer_mb.ml`](/home/matthias/prog/janestreet/emulator-wt-multi-proto/prototypes/multi-proto/sequencer_mb.ml:35)); push is suppressed when full ([line 105]). Pop and push cannot target the same inbox in one cycle because only one thread executes per cycle.
- Both implementations use the configured low address bits for failure targets ([`isa_mb.ml`](/home/matthias/prog/janestreet/emulator-wt-multi-proto/prototypes/multi-proto/isa_mb.ml:131), [`sequencer_mb.ml`](/home/matthias/prog/janestreet/emulator-wt-multi-proto/prototypes/multi-proto/sequencer_mb.ml:45, 57)).
- Both compare WAITC’s selected bit to its value, and otherwise use the same deadline-based fail-or-stay rule ([`isa_mb.ml`](/home/matthias/prog/janestreet/emulator-wt-multi-proto/prototypes/multi-proto/isa_mb.ml:195), [`sequencer_mb.ml`](/home/matthias/prog/janestreet/emulator-wt-multi-proto/prototypes/multi-proto/sequencer_mb.ml:63, 106)).
- With SHO capture clear, the RTL capture bit is zero; with capture set, both shift the sampled pin into the vacated accumulator bit ([`isa_mb.ml`](/home/matthias/prog/janestreet/emulator-wt-multi-proto/prototypes/multi-proto/isa_mb.ml:159–161), [`sequencer_mb.ml`](/home/matthias/prog/janestreet/emulator-wt-multi-proto/prototypes/multi-proto/sequencer_mb.ml:51, 82)).

## Test weaknesses

- **Lockstep does not compare much of the state it claims to validate.** `agrees` checks pins, host and port handshakes, PCs and inbox counts ([`harness_mb.ml`](/home/matthias/prog/janestreet/emulator-wt-multi-proto/prototypes/multi-proto/harness_mb.ml:61–64)). It does not compare per-thread accumulators, counters or deadlines; inbox contents or head pointers; or the current thread. A bug in those states can escape until it changes a checked output—and may remain invisible if it does not do so during the run.
- The extension test checks pins, host handshakes, PCs and that no port transfer occurred ([`lockstep.ml`](/home/matthias/prog/janestreet/emulator-wt-multi-proto/prototypes/multi-proto/lockstep.ml:65–71)), not internal state or instruction-by-instruction equivalence. Random testing also does not establish equivalence for all programs.
