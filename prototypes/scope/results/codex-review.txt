1. **Major — The 0.79 GHz aperture is a model result, not an independently validated SPICE result.** `pad_kick.py` computes the aperture weights and frequency response from the fitted ODE (`pad_kick.py:41–74`). The ODE parameters were fitted to SPICE step waveforms, with a reported 25.2 mV Va RMS fit error (`padmodel.py:192–214`, `results/padmodel-fit.txt`). Its validation reports a 270 ps maximum edge error and a missed SCK recrossing (`results/padmodel-validate.txt`). The SPICE aperture check is a small set of 200 ps kick cases; it does not validate the 500 ps aperture used for the 0.79 GHz claim (`results/pad2-aper.txt`, `pad_kick.py:81–82`). So the claim is supported by the ODE calculation, but the README presents more confidence than this SPICE check establishes. The “integral 1.03” tests the model’s DC response, not its accuracy on arbitrary waveforms.

2. **Major — The demos use the same linear aperture tables for the simulated device and the host’s inverse model.** `KickLinear` loads `results/kick.npz` for both the delay curve and weights (`acq.py:99–116`); `demo_sck.py` uses it to generate the readings and to reconstruct them (`demo_sck.py:33, 117–120`). `demo_eye.py` does likewise (`demo_eye.py:100–103, 1025–1029`). Its aperture “truth” is also calculated from those same weights (`demo_sck.py:167–168`). The reported errors therefore measure noise, quantisation, and chosen calibration effects under a matched model; they do not test whether a real pad follows that model.

3. **Major — The eye trigger and timing fit use hidden truth.** `demo_eye.py` finds pattern matches from the generated symbol levels and computes their threshold crossings directly from the known waveform (`demo_eye.py:967–981`). Those crossings are then used to construct the trigger timestamps and fit the symbol period (`demo_eye.py:987–990`). That skips the matcher and trigger-pad detection errors a chip would incur. Also, the sample-time bookkeeping contains an explicit dead expression referring to the true crossing array, then sets `t_true = ta + centroid` (`demo_eye.py:1030–1033`); this makes the per-sample error comparison use kick launch times, not the reported host time axis. The eye result is not an end-to-end test of the stated trigger-and-sampler chain.

4. **Major — `rx.ml` has access to the true bit index and ideal edge events.** The receiver loop iterates over the transmitted bit index and detects edges using `ln.bits` (`ocaml/rx.ml:105–107`). It timestamps `ln.edges.(i)` directly, then if its inferred count differs from the true index it resets it to `i` (`ocaml/rx.ml:107–113`). Sampling and error scoring also compare against the true bit `ln.bits.(i)` (`ocaml/rx.ml:115–125`). This is not evidence that a receiver can track bit slips from sampled or timestamped observations. The “repeating frame” schedule also uses the true repetition and bit index to select reads (`ocaml/rx.ml:181–190`).

5. **Major — `infer.ml` can become overconfident from finite Monte Carlo tables.** Each table probability is estimated from only 150–4,000 draws, then clamped to `[0.001, 0.999]` (`ocaml/infer.ml:25, 82–87, 131`). The posterior update treats these estimates as exact probabilities (`ocaml/infer.ml:60–63`), and the policy stops once its posterior reaches 0.999 (`ocaml/infer.ml:39–45`). It does not account for uncertainty in the table estimates, so a noisy estimate near the clamp can drive premature stopping. The results report zero errors in small quick trial counts (for example, 0/60), which does not establish a 0.1% error target (`results/infer-quick.txt`).

6. **Major — The “decode” comparisons are weak and not uniformly comparable.** For frames, the fixed schedule reads bit indices in order and stops under the same posterior rule; it is not a conventional decode-all baseline, despite the description (`ocaml/infer.ml:133–138`). Other questions omit a decode row from the actual output and instead compare against hand-estimated capture sizes (`ocaml/infer.ml:167–168, 243–244, 279`). The README’s 2–16 versus 64–4,000 headline therefore combines model-based sequential results with rough, scenario-dependent baselines, not a controlled comparison (`README.md:22–24, 227–241`).

7. **Major — The random-demodulator table is an idealised acquisition model.** The ideal comparator samples an instantaneous threshold of the dithered waveform (`ocaml/cs.ml:435–438`); only the “pad” path runs the pad ODE, and it uses one persistent threshold offset that changes only occasionally (`ocaml/cs.ml:439–452`). Neither path simulates the proposed four-pin random DAC, its electrical loading, nor a measured dither transfer; those are explicitly assumed (`ocaml/cs.ml:424–426`). The bit-times-times-chipping and sum construction is internally coherent for the assumed model (`ocaml/cs.ml:453–457`), but the success table does not validate a physical random-demodulator front end. The README’s “dither/noise folding” conclusions should be read as simulation-specific, especially with only 3–6 trials per cell (`results/cs.txt`).

8. **Minor — Some README result references cannot be checked against the checked-in result files.** The tree contains `results/rx-quick.txt` and `results/infer-quick.txt`, but no `results/rx.txt` or `results/infer.txt`; the README points to the latter for the receive and inference claims (`README.md:206–214, 227–241`). The quick files are explicitly 20,000-bit or 60-trial runs, not the full runs implied by the README.

**Verdict:** The files show plausible exploratory simulations, but the headline performance conclusions are not established as chip capabilities. The aperture and kicked-sampling demonstrations are substantially self-consistent simulations with shared truth and host models; the eye trigger and receive simulations additionally grant the simulated receiver information it would not have. Treat the bandwidth, eye, receive, and few-sample inference claims as hypotheses requiring independent models or hardware evidence.
