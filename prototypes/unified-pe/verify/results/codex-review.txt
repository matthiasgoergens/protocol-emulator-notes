## Highest impact: the verifier tests a different PE contract in important ways

- **Architecture note’s tile mode is not what the tile demo tests.** The note says a tile PE reloads both `S` and `K` every 16 pixels ([architecture-v0.md](/home/matthias/prog/janestreet/emulator-wt-upe-model/notes/architecture-v0.md:277)). The demo reloads `S` through the init chain, but holds one constant `K = tile_col` throughout ([cells.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/cells.ml:151), [cells.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/cells.ml:172)). Thus it verifies a one-colour bitmap renderer, not the note’s tile mode with per-tile configuration reload.

- **The CRC-32-with-gaps result is conditional on a proposed extension, not the architecture as written.** The note’s stream rule steps when `A` is valid ([architecture-v0.md](/home/matthias/prog/janestreet/emulator-wt-upe-model/notes/architecture-v0.md:264)); `follow` is explicitly marked as a proposed addition in the spec ([spec.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/spec.ml:23), [spec.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/spec.ml:26)). `crc32_run` compares continuous operation against `Follow` with gaps, then separately prints the both-streams-with-gaps failure ([cells.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/cells.ml:526), [cells.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/cells.ml:609)). The result file reports all 21 ISO-HDLC messages wrong in both the no-follow cases, including the **no-gap** control ([cells.txt](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/results/cells.txt:18)). So the evidence supports “this particular paired configuration needs the proposed follow behaviour to handle gaps,” but does **not** establish that gaps alone cause failure: the no-gap comparison also fails, and the high PE’s `follow` mode changes its step rule.

- **Array broadcast chaining is only demonstrated for one 12-PE GPS correlator.** The note provides a segment-local broadcast feed ([architecture-v0.md](/home/matthias/prog/janestreet/emulator-wt-upe-model/notes/architecture-v0.md:292)); chaining is proposed in the spec ([spec.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/spec.ml:104)). GPS sets the second joined segment to take the previous segment’s broadcast and checks 12 accumulated offsets ([cells.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/cells.ml:319), [cells.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/cells.ml:336), [cells.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/cells.ml:366)). This shows that chaining serves this 12-PE case. It does not test the claimed threshold of “more than 8,” compare alternatives, or establish that every such correlator needs chaining.

## Weaker checks and shared assumptions

- **The CRC reference is algorithmically independent of the PE, but shares input conventions.** `refs.ml` uses textbook CRC loops ([refs.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/refs.ml:21)); however, both the test and reference derive bit order from the same `Refs.crc.refin` field ([cells.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/cells.ml:500), [refs.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/refs.ml:5)). The catalogue check is against constants, but only the CRC values used there provide an external anchor; it does not independently validate the test’s message-bit stimulus construction.

- **The reported 41 planted faults validate the fault harness, not full design correctness.** Fault controls compare RTL against the model, and the model has corresponding shared-fault switches ([model.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/model.ml:22), [upe_rtl.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/upe_rtl.ml:1)). `controls.txt` reports all 41 caught ([controls.txt](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/results/controls.txt:83)); that is useful RTL/model sensitivity evidence, but not evidence that the model matches the architecture note. The external cell checks cover some of that gap, unevenly.

- **Some “PASS” rows have very few independent outcomes.** GPS reports 13 checks for 12 PE values plus a peak assertion ([cells.txt](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/results/cells.txt:7)); min-plus reports only 4 edge outputs, and sorting reports 9 checks ([cells.txt](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/results/cells.txt:9), [cells.txt](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/results/cells.txt:10)). The long lockstep campaign is broad random agreement between model and RTL, not an independent correctness oracle ([lockstep.txt](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/results/lockstep.txt:1)).

- **Tile placement is shown to work under one carefully chosen schedule, not to be necessary.** The demo places the renderer at PE 2 in segment 1 and schedules writes in two gaps every 16 pixels ([cells.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/cells.ml:141), [cells.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/cells.ml:163)). It does not test alternative placements, segment sizes, or schedules. The result supports “this configuration works with those gaps,” not “tile rendering works only when the renderer is alone in a 2-PE segment.”

- **Sentinel and edge coverage is mixed.** The sprite test deliberately includes solid overlapping sprites and checks 256 outputs per line ([cells.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/cells.ml:99), [cells.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/cells.ml:134)). By contrast, min-plus’s random candidates are 2,000–21,999 while infinity is `0x7fff`, so its inputs do not exercise infinity or overflow at the input boundary ([cells.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/cells.ml:451), [cells.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/cells.ml:461)). Sync tests check the computed soft scores, but the listed `score >= 6` hits include random false positives; the test verifies arithmetic, not detector selectivity ([cells.ml](/home/matthias/prog/janestreet/emulator-wt-upe-model/prototypes/unified-pe/verify/cells.ml:420)).

## Findings that hold, with narrower wording

- **CRC-32 pair:** The logged experiment shows the tested stream-mode pair fails on its supplied traffic without `follow` (21/21 wrong), and the gaps case with `follow` is included in passing cell checks. It does not isolate gap handling as the cause: the no-gap/no-follow control also fails (21/21). This is a real architectural risk for the tested configuration, but the broad claim “CRC-32 fails in stream mode without follow” is too broad without isolating the mode and alignment effects.

- **Broadcast correlators:** The 12-offset GPS test succeeds with broadcast chaining across the 4|8 segment boundary. It establishes utility for that setup, not that all correlators wider than eight require chaining.

- **Tile layer:** The configured one-colour tile demo passes 256 checks with its renderer in the 2-PE segment and scheduled gaps. It does not implement per-tile `K` reload as described in the note, and does not establish the claimed placement or gap necessity.
