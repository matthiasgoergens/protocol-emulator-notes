     2	
     3	The competition's stretch goal, 1.5 Mbit/s USB, built twice and checked against one independent

    83	## The firmware: what it does and how far the original ISA gets
    84	
    85	The chip clock is 60 MHz. A low-speed bit is 40 clocks, so one thread gets 10 instructions per
    86	bit. The threads divide the work as follows.
    87	
    88	- **T0, the bit layer: original instruction set, 63 of 64 words** (`firmware.ml`).
    89	  - It follows the line with deadline waits: a software DPLL that re-times on every edge.
    90	  - It also decodes NRZI, removes stuff bits, detects EOP (SE0) and bus reset, and treats a
    91	    seventh one as an abort.
    92	  - It publishes each bit as VALUE plus a rising STB on internal pins.
    93	  - The same programme runs on the original sequencer's interpreter and RTL, through the
    94	    original files (symlinked), decoding random packets bit-exact:
    95	    - 13 host clock errors from -1.5 % to +1.5 %, 60 packets each;
    96	    - it keeps working from -4 % to +2 %.
    97	  - Pure firmware therefore covers everything below the byte: clock recovery, line code,
    98	    stuffing, framing.
    99	- **T1: IN tokens and the host's ACK.** 180 words.
   100	  - It reads the PID and the token's two bytes and compares them with precomputed bytes
   101	    (address, endpoint and CRC5 included) using SKNE.
   102	  - It answers with data streamed from the reply FIFO, or with NAK or STALL from immediates.
   103	  - It also arms the CRC assist after every PID and disarms it for anything but DATA0/1, so a
   104	    packet with a bad PID can never pass the CRC check. That is the data PID check, done in
   105	    time.
   106	- **T2: SETUP and OUT.** 186 words.
   107	  - It checks the token, then forwards the data packet to the controller (tagged events plus
   108	    bytes).
   109	  - At the EOP it checks the abort flag and CRC_OK, and answers ACK or STALL.
   110	- **T3 is free** for the application.
   111	- **The controller (`controller.ml`) is off the real-time path.** It stands in for software on
   112	  the chip's host side.
   113	  - It keeps the USB state and precomputes every reply as a symbol stream (`fw_codec.ml`: CRC16,
   114	    stuffing, NRZI, EOP, packed four symbols per byte).
   115	  - It patches the programme: the token bytes after SET_ADDRESS, and per state the reply
   116	    choices (data, NAK or STALL on IN; ACK or STALL after OUT data).
   117	  - It needs to answer an event within the shortest data packet (1,280 clocks). The tests use
   118	    latencies of 20 to 1,100 clocks, plus one session where it takes 5,000 clocks to prepare
   119	    each reply and the firmware NAKs meanwhile.

   138	### The generic assist: a programmable CRC unit (`crc_unit.ml`)
   139	
   140	The firmware drives three signals on sequencer pins (bit strobe, value, enable) and reads one
   141	back (ok). A frame signal qualifies the strobes. Protocol knowledge is configuration: polynomial,
   142	initial value, residue, bit order (LSB or MSB first) and how many leading bits to skip, at widths
   143	up to 16 (32 for Ethernet is a wider register). The same unit serves:
   144	
   145	- USB CRC5 and CRC16;
   146	- CAN CRC15, MSB first;
   147	- SMBus PEC and 1-Wire CRC8;
   148	- HDLC and SD CRC16-CCITT, and SD CRC7;
   149	- at width 32, Ethernet's FCS.
   150	
   151	The model and RTL agree over 200,000 random clocks for USB CRC16, USB CRC5 and CAN CRC15, both as
   152	the fixed unit and as the programmable one. It needs no USB-specific logic. The PID skip is done
   153	by the firmware arming it after the PID.
   154	
   155	The reply FIFO is the other piece of hardware. It is a 4-byte FIFO in front of the sequencer's
   156	host port, with its non-empty flag on a pin, and it is generic: any protocol with a response
   157	deadline needs its first bytes on chip. It is modelled in OCaml and shared by both systems; there
   158	is no RTL for it yet. The pin streamer's FIFO is the obvious implementation.

   160	### What the other generic pieces would buy
   161	
   162	- **Bit stuffing and NRZI unit** (programmable run length and polarity: USB 6 ones, CAN 5 equal
   163	  bits, HDLC 5 ones). It would free T0 and the three pins between T0 and the consumers. At low
   164	  speed firmware does this, so the unit is not needed here. At full speed (4 clocks per bit)
   165	  it is.
   166	- **Pin sampler.** Its timed mode samples every period after a trigger, with no re-timing on
   167	  edges. Over a 100-bit packet at ±1.5 % that slips by more than a bit, so it cannot receive
   168	  USB. Its clocked mode could capture VALUE on STB into a FIFO, for the host. The sequencer
   169	  cannot read that FIFO.
   170	- **Pin streamer.** It could send the precomputed replies (width 2, period 40, idle = released).
   171	  It would need a trigger input so that firmware starts it at the right clock, since today it
   172	  starts when a word arrives, and a choice among queued replies (NAK, STALL, data). SHO pair
   173	  mode in T1/T2 does this with no new block.
   174	- **Systolic matcher** (`matcher_exp.ml`, on its closed-form specification):
   175	  - Fed one sample per decoded bit, with T0's strobe as a clock enable the prototype lacks, a
   176	    16-cell template of the 16 bits after an IN token's PID found all 13 target tokens in
   177	    159,016 bits of random traffic.
   178	  - It also hit 46 OUT/SETUP tokens with the same tail (the PID lies outside the template) and
   179	    1 chance match in data (2.4 expected).
   180	  - So it can recognise tokens, but only framed (right after a PID) and one matcher per endpoint
   181	    (10,015 µm² each). SKNE does the same job for part of 2,510 µm².
   182	  - The matcher's place is sync and delimiter search in raw oversampled streams at higher
   183	    rates. There the offset is unknown and there is no bit clock yet.

   190	| clock | SETUP data, answered ACK by T2 | clock | IN token, answered with FIFO data by T1 |
   191	|---:|---|---:|---|

   194	| 40 | T0's end-of-packet strobe (after the 6-slot low) | 44 | T0's end-of-packet strobe |

   202	
   203	- **The firmware has decided within 46 to 65 clocks**, before the host's EOP has even ended
   204	  (clock 80).
   205	- It then waits on purpose: the host drives its final J until clock 120, and the device may
   206	  drive J only after that. At 1.5 % slow the host ends at clock 122.

   208	  2.6 to 2.7 bits.

   210	  turnarounds measured 2.51 to 6.00 bits, inside the 2 to 6.5 limit.

   215	deliberate 6-slot low before the end-of-packet strobe.

   217	## What went wrong on the way (all found by the random and tolerance tests)
   218	
   219	- **The sample point walked off the end of the bit.**
   220	  - A one took 7 slots to publish, and an edge arriving meanwhile was timed late. That late
   221	    edge set the next sample point late, and every one-zero pair added more.
   222	  - A later version assumed such an edge was at its nominal place. That kept a late sample point
   223	    late, and 0xFF bytes (stuff bits every 7 bits) then drifted it out of the bit with the host
   224	    1 % fast.
   225	  - The fix: an edge seen during the publication of a one is placed in the middle of the window
   226	    in which it must have happened. That pulls the sample point back.
   227	- **Runs of zeros were never timed.** Coming back from a zero took a full bit (10 slots). With
   228	  the host fast, each edge had already happened when the thread began waiting for it. The zero

### Findings

- **Low — bad non-DATA PID can leave CRC armed.** T1 enables CRC after *every* PID at [firmware.ml:187–188](/home/matthias/prog/janestreet/emulator-wt-proto-usb-ls/prototypes/usb-ls/firmware.ml:187). For non-IN PIDs, `notin` drains the packet without disarming CRC; only the `drain1` path does so ([firmware.ml:193–195](/home/matthias/prog/janestreet/emulator-wt-proto-usb-ls/prototypes/usb-ls/firmware.ml:193)). In particular, DATA0/DATA1 fall through to `dkeep`, which waits for IDLE and returns to `idle1` without clearing CRC_EN. T1 then clears it at the next SOP, but T2’s data receiver waits for IDLE to fall before syncing for the next packet ([firmware.ml:235–236](/home/matthias/prog/janestreet/emulator-wt-proto-usb-ls/prototypes/usb-ls/firmware.ml:235)). So a host data packet arriving immediately after that non-DATA packet can be missed by T1’s PID check while T2 processes it; the claim that this path guarantees a bad PID cannot pass CRC is unsupported. The logs exercise bad-CRC SETUP data, but don’t establish this back-to-back PID case.

- **Low — silence assertions can pass vacuously for a missing response.** `expect_silence` treats `No_reply` as success ([bench.ml:219–222](/home/matthias/prog/janestreet/emulator-wt-proto-usb-ls/prototypes/usb-ls/bench.ml:219)); it does not check that the device answered preceding valid traffic. Directed enumeration and report checks do require replies, so the overall directed run is not wholly vacuous, but a broken device could still pass an individual “must ignore” assertion by never answering that packet.

The firmware log reports 64 words used, 60/60 packets per clock offset, zero mismatches ([run-fw-8seeds.log:12–24](/home/matthias/prog/janestreet/emulator-wt-proto-usb-ls/prototypes/usb-ls/run-fw-8seeds.log:12)). **Supported.**

- **Lockstep:** The full-system bench compares pins, host-port effects/readiness, and PCs every clock ([dut_fw.ml](/home/matthias/prog/janestreet/emulator-wt-proto-usb-ls/prototypes/usb-ls/dut_fw.ml), `step` comparison); T0’s original-sequencer harness also compares outputs and PCs each clock ([main_fw.ml:117–122](/home/matthias/prog/janestreet/emulator-wt-proto-usb-ls/prototypes/usb-ls/main_fw.ml:117)). These checks would detect those compared-state divergences. **Supported, with comparison scope as stated.**

- **Turnaround/contention:** `receive` measures SOP from the host EOP J edge and flags values outside 2–6.5 bit times ([bench.ml:98–120](/home/matthias/prog/janestreet/emulator-wt-proto-usb-ls/prototypes/usb-ls/bench.ml:98)); `tick` flags simultaneous host/device drive ([bench.ml:55–65](/home/matthias/prog/janestreet/emulator-wt-proto-usb-ls/prototypes/usb-ls/bench.ml:55)). The logs show late/early controls caught, including contention for early firmware response ([run-fw-8seeds.log:121–124](/home/matthias/prog/janestreet/emulator-wt-proto-usb-ls/prototypes/usb-ls/run-fw-8seeds.log:121)). **Supported.**

- **Encoding collision:** The variant uses SHO bit 6, OUT bit 8, WAITP/JMP/JNZ bits [7:6], and opcode E ([isa_ls.ml:18–20](/home/matthias/prog/janestreet/emulator-wt-proto-usb-ls/prototypes/usb-ls/isa_ls.ml:18)); the cited master extension uses SETP/SHO bits [1:0] and SHI bit 7. No collision is evident in these fields. **Supported for the stated extension.**
