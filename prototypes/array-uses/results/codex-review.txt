## Findings, most important first

1. **The claimed eight-PE synthesiser configuration does not fit the prototype.** The README says eight PEs allow “two voices plus noise” ([README.md:53–55](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/README.md:53)). But `synth.ml` assigns **3 PEs per square voice**, **2 for noise**, and **2 more for offset and sigma-delta** ([synth.ml:4–15](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/synth.ml:4), [synth.ml:37–46](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/synth.ml:37)): two voices plus noise therefore need **10 PEs**, unless some function is removed or remapped. This weakens the “on their own about 8” size verdict, though the receiver still fits two channels in eight PEs.

2. **The receiver’s planted-fault check does not substantiate “every channel” as written.** The README says every channel’s correlation falls to at most 0.05 ([README.md:143–144](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/README.md:143)). In the cited fault output, channel 3’s beep correlations are `nan` because the analysed window contains no beep ([ddc_fault_check.txt](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/results/ddc_fault_check.txt)); `analyse_ddc.py` prints the best fit but has no threshold assertion or failure condition ([analyse_ddc.py:36–48](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/analyse_ddc.py:36), [analyse_ddc.py:55–75](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/analyse_ddc.py:55)). The control does show the fault suppresses the active stations on channels 0–2, but the stated all-channel check is not actually established.

3. **Several host rates are compiler-model rates, not RP2350 comparisons, and the model can be optimistic.** `mca.py` compiles generic Cortex-M33 code at `-O2`, selects the shortest backward-loop span, and feeds that assembly to llvm-mca ([mca.py:3–11](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/host/mca.py:3), [mca.py:66–81](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/host/mca.py:66)). It models single-cycle SRAM and no bus contention or interrupts; adding a flat two-cycle branch penalty does not model memory stalls, DMA contention, or total-function setup and exit costs ([evaluate.ml:3–9](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/evaluate.ml:3)). The table correctly labels these as static estimates, but the strong host/array ratios—especially for host DSP and memory-heavy loops—need an RP2350 run before being treated as measured comparisons. I found no clear case where the cited assembly was obviously counted at an unfairly slow loop rate; the bigger issue is that the model omits real-system costs and benefits.

4. **`k17_insert` compares a per-step host count with a per-sample application need.** The host kernel and table item are one compare-shift step ([kernels.c:208–214](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/host/kernels.c:208), [evaluate.ml:111–115](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/evaluate.ml:111)); the need is one 60 MS/s input stream. The table’s 960 M array rate is compare-shift steps per second, not sorted samples per second. A 16-stage insertion needs up to 16 such steps per sample, so the relevant worst-case throughput is **60 M samples/s**, not 960 M. The prose does acknowledge “16 steps per sample” for rising data, but the table’s headline rate and 25.6× ratio compare unlike items. The marginal verdict is less affected because it has an override, but that ratio should not be used as evidence for array size.

5. **“Does not fit” is stronger than the evidence for DTW and edit distance.** The README says these do not fit a PE with one link and a static operation, while the evaluation assigns DTW a five-clock estimate *with a second link* and edit distance 128 PE-clocks per character ([README.md:223–234](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/README.md:223), [evaluate.ml:62–74](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/evaluate.ml:62)). That supports “no demonstrated direct mapping at the quoted rate,” not impossibility. Both recurrences can be scheduled through bank reads/writes and multiple PE passes; such a mapping may be slow, but the README does not show a lower bound ruling it out. The Viterbi discussion itself accepts a bank-streamed, multi-pass mapping ([README.md:39–41](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/README.md:39)), which makes the categorical distinction less clear.

6. **The receiver result validates a synthetic signal chain, not a practical direct-sampling receiver.** The prototype assumes eight ADC pins can feed a segment at 60 MHz ([README.md:121–131](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/README.md:121)); the architecture’s pin/feed path does not yet establish that capability ([README.md:253–256](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/README.md:253)). The model also uses synthetic stations, injected Gaussian noise, and a tuned empty channel; the reported correlations demonstrate demodulation under that scene, not sensitivity, blocker tolerance, antenna/front-end performance, or robustness to clock/sample imperfections. This is a valid candidate workload, but the evidence for “earns its area” remains conditional on a substantial interface assumption.

7. **The synth check validates its own schedule and pause assumptions more than independent output correctness.** Its reference is generated from the schedule logged by the same simulator, and it hard-codes a 1,017-clock pause model ([analyse_synth.py:3–9](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/analyse_synth.py:3), [analyse_synth.py:16–27](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/analyse_synth.py:16)). The gain and semitone control are useful checks that the rendered waveform follows that schedule, but they do not independently validate the tune scheduler, the physical configuration-link timing, or the assumed pin behaviour during pause. The code reports `bad_loads` rather than failing when it is nonzero ([synth.ml:130–156](/home/matthias/prog/janestreet/emulator-wt-array-uses/prototypes/array-uses/synth.ml:130)); the recorded zero mismatches are evidence for this run, but not an enforced regression check.

## Claims that held up against the cited files

The main arithmetic in the evaluation output matches its source calculations: the receiver’s 240 M sample-channels/s is 16 PEs × 60 MHz ÷ 4 clocks/item; the two-core host estimate is 300 MHz ÷ 17 cycles/item = 17.6 M; and the receiver correlations and −9.5 dB image agree with the cited result files. The Viterbi and DTW costs are explicitly marked estimates, and the README’s open section says their mappings are sketches. I found no obvious transcription mismatch in those cited output numbers.
