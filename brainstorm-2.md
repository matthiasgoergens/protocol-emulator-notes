## 1. The constraints that shape everything

| Resource | Budget | Source |
| --- | --- | --- |
| Area | 6x4 tiles, about 24K cells; 8x4 under consideration | blog post |
| Tile | about 200 µm x 150 µm, about 1K cells | blog post |
| Pins | 8 in, 8 out, 8 bidirectional, plus `clk`, `rst_n`, `ena` | TT gpio spec |
| Clock | 1 Hz to 66.5 MHz, generated by the RP2040 on the demo board | TT clock spec |
| Pad limits | 33 MHz max output toggle, 66 MHz max input | TT gpio spec |
| IO supply | 3.3 V on the demo board, 4 mA drive | TT gpio spec |
| SRAM 1024x8 | 2x1 tiles, 76 % of them | TT memory spec |
| SRAM 1024x16 | 2x2 tiles, 60 % of them | TT memory spec |
| SRAM 1024x32 | 3x4 tiles, 31 % of them | TT memory spec |
| SRAM 512x8 dual-port | 2x2 tiles | TT memory spec |
| DFF density | about 320 DFFs per tile; latch RAM about 512 bits per tile | TT memory spec |
| Deadline | 18 January 2027; shuttle March 2027 | blog post |

Consequences:

- **10 Mbit Ethernet is reachable but only with a dedicated serialiser.**
  Manchester at 10 Mbit/s is a 20 MHz toggle rate, under the 33 MHz pad limit,
  but at 66 MHz that is 3.3 clocks per half-bit. Nothing that issues one
  instruction per pin change can do it; a shift register with a programmable
  divider can. Low-speed USB at 1.5 Mbit/s is easy by comparison.
- **One 1024x16 SRAM costs four tiles and leaves about twenty.** A small
  16-bit core is 3K to 5K cells, so "several small cores plus SRAM" fits.
  "Many small things" is a viable shape, and it is the shape the firing-squad
  work already knows how to build.
- **The RP2040 is on the board.** It is the clock source, the loader, and a
  real UART, SPI and I2C counterparty. Design the loading protocol and the
  tests around it from day one.
- **Pin budget is tight if the loader is parallel.** Reserve as few pins as
  possible for loading (a serial rule-book or program load over two pins, as
  in both puzzle chips) so that 20 or more pins remain for protocols.
  10BASE-T needs TX+, TX-, RX+ and RX- through external magnetics; CAN needs
  an external transceiver; USB needs two bidirectional pins.

## 2. Architecture ideas

Ordered roughly by how far they are from the reference designs (PIO, PRU).

### 2.1 Table-driven pin cells, the firing-squad descendant

Overlaps brainstorm.md items 1 and 6; this is the concrete version.

Each pin gets a Mealy machine whose next-state function is a lookup table in
SRAM rather than logic. Index bits, for a 1024-entry table:

| Field | Bits |
| --- | --- |
| current state | 5 |
| sampled pin | 1 |
| left neighbour state (or a summary of it) | 2 |
| timer expired | 1 |
| byte-shifter flag (bit available, byte done) | 1 |

Output word: next state, pin drive, pin enable, timer reload select, shifter
strobe. Cells talk only to their neighbours, exactly like the shells in the
firing-squad rack, so a protocol is a chain: a bit-timing cell feeding a
byte-framing cell feeding a message cell. Timing is exact by construction
because every transition takes one clock.

Why it is novel: nobody ships a cellular-automaton peripheral. Reprogrammability
after fabrication is total because the table *is* the programme. The serial
rule-book loader, the neighbour-only communication and the Hardcaml testbench
all exist already in `hardcaml_firing_squad/`.

Costs: a 1024x8 table per cell is two tiles, so full-width tables for eight
cells do not fit. Options: share one SRAM across cells with time-multiplexed
lookups (the firing-squad chip already inspects one shell per tick), or use
much smaller per-cell tables in latch RAM (512 bits per tile) and keep the
big table for one "master" cell.

### 2.2 Time-triggered ISA: the programme is a waveform

Instructions carry a timestamp: "at cycle T, drive pins X, then branch on
input Y". Run-length coding keeps the stream small. It is the inverse of the
VCD-replay tooling in `hardware-2026-08/work/replay_vcd.py`: record a real
device's waveform, edit it, replay it with reactions. Decoding becomes pattern
matching on timestamped edges, which is brainstorm.md's item 2 seen from the
transmit side. Good fit for "protocol *emulation*" as opposed to "protocol
implementation": you can replay a captured session from a device you do not
have.

### 2.3 Transport-triggered architecture

The only instruction is "move". Function units are pin registers,
down-counters, shifters, a comparator and a CRC unit. Every instruction takes
one cycle, so timing is readable straight off the listing, and a wide
horizontal encoding maps well onto a 16-bit or 32-bit SRAM word. Open-source
TTAs are rare (TCE from Tampere is the main one) and none has been taped out
as a pin-timing engine.

### 2.4 Barrel-threaded scheduler, Propeller or XMOS style

Four hardware threads issue round-robin. Each thread owns exactly a quarter of
the cycles, so it has zero jitter whatever the others do, and a UART-to-SPI
bridge is two threads and a mailbox. At 66 MHz each thread sees 16.5 MHz,
which is enough for UART, SPI and I2C at any usual rate. The fast protocols
still go through a dedicated shifter. This is the cheapest way to get several
concurrent protocols with provable timing, and it composes with 2.1: the
threads do byte-level logic, the cells do bit-level timing.

### 2.5 Bit-serial one-bit cores, MC14500 style

Protocols are bit-serial anyway. A one-bit ALU core is a few hundred cells, so
one per pin is affordable, and the area saved goes to SRAM or a shifter.
Programme words are tiny, so a 1024x8 SRAM holds a lot of programme. Pairs
naturally with 2.1, and the two can share a loader.

### 2.6 Sub-cycle timing hardware

Same as brainstorm.md item 4. Additional point: a delay-line time-to-digital
converter on inputs is the only way to *decode* faster than the clock allows,
and it is the one block whose real value can only be measured in silicon,
which is exactly what the prize provides. Keep it a bolt-on so a failure to
close timing does not sink the main design. Calibrate against the known clock
period at run time so PVT spread becomes a measurement, not a bug.

### 2.7 Protocol tester, not only emulator

Same as brainstorm.md item 3 (fault injection). Add: arbitration loss on I2C
multi-master, clock stretching beyond spec, deliberate setup-time violations
by way of 2.6, and bit-error injection into CRC-protected frames. A chip that
misbehaves on purpose is test equipment, and it is "novel functionality beyond
stated protocols" in the judges' own words.

### 2.8 Logic analyser as the dual use of the SRAM

Same memory holds programme or capture buffer. A small trigger matcher, ideally
an NFA over sampled pin vectors like a bench analyser's trigger, and the
decoder reuses the matcher. The dual-port 512x8 macro makes capture and
execution concurrent if that matters.

### 2.9 Boot paths and first-silicon hygiene

- A hardwired UART or SPI-flash bootloader in ROM so the chip runs standalone
  from the QSPI Pmod (16 MB flash, two 8 MB PSRAM on the standard Pmod).
- A burnt-in "hello" programme that prints on a UART pin at reset so first
  silicon can be checked in a minute from the RP2040.
- A serial ID or signature readable over the load interface, in the spirit of
  the puzzle chips' message ROMs.

### 2.10 Recommendation

Combine 2.1 and 2.4: a chain of table-driven cells for bit-level timing, fed
by a small barrel-threaded scheduler for byte-level logic, with one 1024x16
SRAM shared between programme and tables. It reuses the working firing-squad
machinery, it is unlike either reference design, and the two halves can be
built and verified by different team members in parallel. brainstorm.md's
headline combination is compatible with this; the difference is which block is
the *engine* and which is the assist.

## 3. Verification methodology ideas

The post lists "novel design and verification methodologies" as a criterion
in its own right.

### 3.1 Close the loop on the GDS

Same as brainstorm.md item 8, with detail: `hardware-2026-08/work/extract.py`
reads GDS, unions polygons per layer, bridges through vias, maps pin labels to
nets; `work/cells.py` interprets the official cell Verilog models mechanically
so cell behaviour is right by construction. Porting means swapping the layer
table and the cell-model directory for IHP sg13g2 (the PDK ships functional
Verilog for every cell). Then run the whole firmware test suite against the
netlist extracted from *our own* final GDS. That is how the floating net in
Jane Street's own puzzle chip would have been caught before tapeout, and it
is a story the judges will recognise.

### 3.2 Executable ISA model versus RTL, in lockstep

An OCaml interpreter for the ISA (or the cell tables) is the specification.
Drive it and the Hardcaml RTL with random programmes from a fixed seed and
compare pin outputs every cycle. This is the puzzle reconstruction's
random-stream equivalence test generalised. `hardcaml_verify` can then give
bounded proofs of timing invariants such as "a wait resumes exactly N cycles
after the edge" and "no two cells drive the same pin".

### 3.3 The RP2040 as the counterparty, before and after silicon

Write the MicroPython tests that talk to the chip through the RP2040's own
UART, SPI and I2C peripherals *before* tapeout, and run them against Verilator
through a socket or a cocotb bridge. The identical scripts then run on the
dev board. One test suite, two targets, and the silicon results are directly
comparable with simulation.

### 3.4 ISA usability measured with an agent

Give a language model the ISA document and ask it to write the I2C master and
the USB low-speed device unassisted, gated by the differential tests of 3.2.
Report how far it gets and where it stalls. A measured expressiveness score is
a novel methodology, an honest answer to the "AI-assisted verification" theme,
and a real test of whether the ISA is usable by anyone but its authors.
brainstorm.md item 11 is the same idea with a formal backstop; both can run.

### 3.5 Mutation testing of the testbench

Inject small RTL mutations (inverted condition, off-by-one timer, swapped
mux input) and count how many the suite catches. Report the number. Few
hardware entries will have a measured test-suite strength.

### 3.6 Look where you stopped looking

Keep a file of every suppressed warning, every skipped test and every
`if false`, and audit it before tapeout. The puzzle's extractor had reported
the undriven net all along and nobody read the report.

## 4. Prior art to read before committing

A day here saves weeks. The judges will know all of these.

- RP2040 PIO and TI PRU, named in the post.
- Cypress PSoC universal digital blocks: small datapath plus PLD per block.
- XMOS xCORE: hardware threads with guaranteed timing, ports with timestamps.
- Parallax Propeller: eight cogs round-robin, no interrupts.
- GreenArrays GA144: 144 tiny asynchronous Forth cores, neighbour-only
  communication. Closest existing thing to 2.1 plus 2.5.
- Padauk FPPA: several hardware threads in a sub-dollar microcontroller.
- Motorola MC14500 ICU: the one-bit industrial control unit.
- Bus Pirate and Glasgow Interface Explorer: the software-side prior art for
  "one device, every protocol".
- Tampere TCE: the open-source TTA toolchain.
